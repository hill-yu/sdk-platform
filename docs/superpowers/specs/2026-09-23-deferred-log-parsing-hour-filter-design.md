# 日志后置解析、小时筛选与容量控制设计

> 日期：2026-09-23
> 基线：`86a03f3`
> 状态：设计已确认，待用户审阅正式规格
> 时区：所有业务筛选统一使用 `Asia/Shanghai`（UTC+8）

## 1. 背景与生产证据

当前日志上报会同时写入原始事件和一条 `record_index=-1`、`status=pending` 的解析占位记录。Admin API 启动后每秒扫描一次 pending，单批最多 50 条，并在 API 进程内逐条调用解析器。该实现目前没有积压，但日志量增长后会持续消耗 CPU、增加数据库写入与索引维护，并使 Admin API 与解析任务争用同一进程资源。

2026-09-23 生产只读审计结果：

- 服务器为 4 vCPU、3.9 GiB 内存；约 2.8 GiB 内存可用；根盘剩余约 62 GiB；
- PostgreSQL 数据库约 216 MiB，连接数 10/100，无锁等待和超过 60 秒的长事务；
- 最近 24 小时日志约 21,863 条，最近 7 天约 50,818 条；当前 `pending=0`；
- 最近 24 小时平均流入约 0.25 条/秒，观测峰值约 0.67 条/秒；
- Nginx 最近 24 小时约 44,974 个请求、278.85 MiB 响应流量；30 秒网卡采样约 RX 0.023 Mbps、TX 0.038 Mbps；
- 当前 CPU、内存、磁盘、数据库与实际网络流量均有明显余量；云厂商套餐带宽上限无法从操作系统确认，仍需以 VPS 控制台为准；
- 当前解析没有形成积压，但批内串行和单条 5 秒超时会在异常输入集中出现时显著降低最坏吞吐。

因此本设计不是为解决当前故障，而是提前将解析从持续自动消费改为管理员显式触发、范围受限、资源隔离的后台任务。

## 2. 目标

1. SDK 日志上报只持久化原始日志，不再自动触发解析。
2. 管理员设置包名和连续北京时间范围后，点击“开始解析”创建后台任务。
3. 解析统计和原始日志均支持开始日期/小时、结束日期/小时筛选。
4. 原始日志页面的 CSV 导出同步小时条件，保证查看和导出范围一致。
5. 解析任务与 Admin API 进程隔离，限制 CPU、内存、并发和任务跨度。
6. 正常日志 10,000 条端到端解析时间不超过 60 秒。
7. 保留原始日志、现有解析结果、重解析能力、断点续跑和回滚能力。

## 3. 非目标

- 不修改 SDK 日志上报请求体。
- 不修改解析器词库和字段含义。
- 不删除历史原始日志或已解析结果。
- 不在本次变更中引入消息队列、Redis、Kafka 或独立服务器。
- 不根据推测增加所有可能的数据库索引；只增加本次任务和筛选实际使用的索引。
- 不承诺异常日志持续触发超时时仍能达到 10,000 条/分钟；该目标适用于通过正常解析路径的日志。

## 4. 总体架构

### 4.1 日志写入链路

```text
SDK POST /api/v1/log
  -> 校验请求
  -> 批量写入 sdk_events
  -> 提交事务
  -> 立即返回 accepted/rejected
```

写入链路不再：

- 插入 `sdk_log_decodes` pending 占位记录；
- 调用解析器；
- 等待解析任务；
- 因解析失败回滚原始日志。

### 4.2 后置解析链路

```text
管理员设置筛选条件
  -> POST /api/admin/log-analysis/parse-jobs
  -> 固化范围和创建时快照边界
  -> 独立 sdk-log-parse-worker 领取任务
  -> 每批读取 200 条原始日志
  -> 独立进程池并行解析
  -> 批量 upsert 解析结果
  -> 提交游标和进度
  -> 完成、失败或取消
```

普通“查询结果”只读取已有结果，绝不隐式创建解析任务。页面刷新、翻页和排序也不得触发解析。

## 5. 解析任务范围与时间语义

### 5.1 必填条件

创建任务必须提交：

- `package_name`；
- `date_from`；
- `hour_from`，整数 `0..23`；
- `date_to`；
- `hour_to`，整数 `0..23`。

可选条件：

- `sdk_version`；
- `device_id`；
- `log_level`：`debug`、`info`、`warn` 或 `error`；
- `force_reparse`，默认 `false`。

单个任务的连续时间范围不得超过 7 天。结束时间不得早于开始时间。

### 5.2 连续北京时间范围

小时筛选不是“每天重复同一小时”，而是起始日和终止日组成的连续范围。

例如：

```text
date_from=2026-09-20, hour_from=8
date_to=2026-09-22, hour_to=17
```

语义为：

```text
2026-09-20 08:00:00 +08:00 <= server_ts
server_ts < 2026-09-22 18:00:00 +08:00
```

后端集中使用一个时间边界函数把北京时间转换为 UTC 半开区间，禁止各服务自行拼接时间。

小时参数必须成对提交。旧客户端不传小时参数时，`hour_from=0`、`hour_to=23`，保持原有全天行为。

### 5.3 创建时快照

任务创建时固化 `snapshot_end`：

```text
snapshot_end = min(请求范围结束, 任务创建时刻)
```

worker 只处理任务创建时已经存在的事件，不追赶任务运行期间持续写入的新日志。新日志需要下一次任务处理，从而保证目标数量、进度和预计剩余时间稳定。

## 6. 任务模型与兼容性

继续使用现有数据库表 `sdk_log_reparse_jobs`，避免生产表重命名风险；ORM 和页面统一使用“解析任务”术语。

新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `job_type` | VARCHAR(16) | `parse` 或 `reparse` |
| `sdk_version` | VARCHAR(20) NULL | SDK 版本精确匹配 |
| `device_id` | VARCHAR(64) NULL | 设备 ID 精确匹配 |
| `log_level` | VARCHAR(16) NULL | 日志级别精确匹配 |
| `force_reparse` | BOOLEAN | 是否覆盖现有解析结果 |
| `snapshot_end` | TIMESTAMPTZ | 创建任务时固化的实际结束边界 |
| `total_count` | BIGINT | 任务目标事件数 |
| `skipped_count` | BIGINT | 已有当前版本结果而跳过的事件数 |
| `batch_size` | INTEGER | 创建时固化的批量大小 |
| `concurrency` | INTEGER | 创建时固化的并行数 |
| `started_at` | TIMESTAMPTZ NULL | 开始时间 |
| `finished_at` | TIMESTAMPTZ NULL | 结束时间 |
| `last_heartbeat_at` | TIMESTAMPTZ NULL | worker 心跳 |
| `cancel_requested_at` | TIMESTAMPTZ NULL | 取消请求时间 |

已有的范围、游标、租约、已处理数、成功数、失败数、状态和错误摘要继续保留。

默认解析任务只处理缺少当前 `decoder_version` 结果的事件。存在旧版本结果但没有当前版本结果时，删除该事件的旧派生结果并写入当前版本。`force_reparse=true` 时覆盖范围内所有匹配事件的解析结果。

现有 `/log-analysis/reparse` 接口保留兼容，并转换成 `job_type=reparse` 的统一任务。

## 7. 独立解析 worker 与性能预算

新增独立 systemd 服务：

```text
sdk-log-parse-worker
```

Admin API 只创建、查询、取消任务，不再启动 `pending_log_parse_loop()` 或 `reparse_job_loop()`。

默认资源参数：

- `LOG_PARSE_BATCH_SIZE=200`；
- `LOG_PARSE_CONCURRENCY=3`；
- 并发范围限制为 `1..3`；
- 全局同时只执行一个任务；
- 使用独立进程池而不是线程池，确保 Python 解析可实际使用多核；
- systemd `CPUQuota=300%`、`MemoryMax=1536M`、`Nice=5`；
- 活跃任务的批次之间不固定 sleep；无任务时轮询间隔 1 秒。

每批流程：

1. 按 `(server_ts, id)` 游标读取最多 200 条；
2. 把必要的事件字段和 `extra` 传给最多 3 个解析进程；
3. 汇总结果；
4. 在主 worker 中批量删除旧派生行并批量 upsert 新结果；
5. 单事务提交本批结果、游标、计数和心跳。

进程终止后最多重复处理当前未提交批次；upsert 和事件级替换保证重复执行结果一致。

### 7.1 一分钟性能门禁

目标吞吐至少为：

```text
10,000 / 60 = 166.67 条/秒
```

上线门禁必须使用生产同规格 4 vCPU 环境和真实结构的脱敏/受控样本执行 10,000 条端到端基准，计时包含：查询、进程间传输、解析、批量写入、事务提交和任务状态更新。

验收要求：

- 总耗时不超过 60 秒；
- 解析期间 SDK 上报和 Admin 健康接口持续成功；
- CPU、内存没有突破 systemd 配额；
- 无任务丢失、重复结果或游标错误。

若基准未达到 60 秒，不得部署。应先定位解析 CPU、进程通信或数据库写入瓶颈；不能通过无限增加并发掩盖问题。异常输入超时使用单独的保护性验收，不纳入正常日志一分钟 SLO。

## 8. API 设计

### 8.1 创建任务

```http
POST /api/admin/log-analysis/parse-jobs
Authorization: Bearer <ADMIN_TOKEN>
```

```json
{
  "package_name": "com.example.app",
  "date_from": "2026-09-20",
  "hour_from": 8,
  "date_to": "2026-09-22",
  "hour_to": 17,
  "sdk_version": "1.0.5",
  "device_id": null,
  "log_level": "info",
  "force_reparse": false
}
```

创建时计算并返回 `total_count`、`skipped_count` 和任务 ID。任意任务处于 `pending`、`running` 或 `cancelling` 时，新的创建请求返回 `409` 和当前任务摘要，避免资源争抢。

### 8.2 查询和取消

```http
GET  /api/admin/log-analysis/parse-jobs/{id}
POST /api/admin/log-analysis/parse-jobs/{id}/cancel
```

状态集合：

```text
pending, running, cancelling, success, failed, cancelled
```

进度响应包括总量、已处理、成功、失败、跳过、当前速度、预计剩余秒数、开始时间、结束时间和脱敏错误摘要。

取消请求不终止正在提交的事务，worker 在当前批次提交后将任务置为 `cancelled`。

## 9. 小时筛选 API

下列接口增加 `hour_from`、`hour_to`：

- `GET /api/admin/log-analysis/summary`；
- `GET /api/admin/log-analysis/details`；
- `GET /api/admin/events`；
- `POST /api/admin/log-exports`。

解析统计接口同时增加可选 `sdk_version`，使查询条件与解析任务一致。

日志导出任务表增加小时字段，worker 使用同一 UTC 半开区间。不得再次出现“页面筛选生效但导出忽略”的不一致。

汇总仍按北京时间日期和包名分组。点击某个日期的明细时，明细范围取该自然日与全局连续时间范围的交集：

- 起始日从 `hour_from` 开始；
- 终止日到 `hour_to` 整小时结束；
- 中间日期为全天。

## 10. 前端设计

### 10.1 解析统计

筛选栏包含：

- 开始日期、开始小时；
- 结束日期、结束小时；
- 包名；
- SDK 版本；
- 设备 ID；
- 日志级别。

操作按钮：

- “查询结果”：只查询已有解析结果；
- “开始解析”：校验必填条件后创建任务；
- “取消任务”：只在 pending/running/cancelling 时显示；
- “重置”。

任务卡片显示状态、目标数、已处理数、成功数、失败数、跳过数、覆盖率、解析速度和预计剩余时间。任务成功后自动刷新当前统计；失败或取消时保留当前页面数据并显示明确原因。

页面同时显示所选范围的：

- 原始日志总数；
- 当前解析器版本已解析事件数；
- 未解析事件数；
- 失败事件数；
- 解析覆盖率。

所有覆盖数量按事件键去重，不能因为一个 `extra` 产生多条解码记录而重复计数。

### 10.2 原始日志

原始日志筛选栏增加开始小时和结束小时。查询、分页、刷新和 CSV 导出始终复用同一已应用筛选条件。

## 11. 异常保护

- 单条解析超时记为该事件失败，不回滚本批其他事件；
- 连续 10 条超时，任务标记 `failed` 并停止；
- 处理至少 100 条后，总失败率超过 20%，任务标记 `failed` 并停止；
- worker 基础设施异常保存脱敏摘要并释放或等待租约过期；
- 错误摘要不得包含完整 `extra`、Token、数据库连接或用户代理；
- 任务重试创建新任务；已成功批次通过当前解析器版本检查自动跳过；
- 日期跨度、小时范围、包名、SDK 版本、设备 ID和日志级别均在 API 层严格校验；
- 任务创建、状态查询和取消均受 Admin Token 保护。

## 12. 数据库索引

保留现有事件和解码索引，并补充：

- `sdk_events(package_name, server_ts)`；
- `sdk_events(package_name, sdk_version, server_ts)`；
- `sdk_log_reparse_jobs(status, created_at)` 继续用于领取任务。

事件表为分区表时，迁移必须验证当前分区和未来分区都获得相同索引定义。

本次不默认增加设备 ID 与 JSONB 日志级别表达式索引。上线后通过查询计划和慢查询证据确认确有需要时再增加，避免无效索引放大写入与磁盘占用。

## 13. 迁移与发布

1. 完成后端、前端、迁移和性能测试。
2. 备份生产数据库、当前 release、前端、systemd 和宝塔 Nginx 配置。
3. 确认当前 pending 数量为 0；如非 0，等待清零或保留原始日志后清理派生占位。
4. 幂等增加任务字段、约束和索引。
5. 删除残留的 `record_index=-1` 占位行；不得删除 `sdk_events` 或有效解析结果。
6. 部署新 SDK API 和 Admin API，停止 Admin 内自动解析循环。
7. 部署并启动 `sdk-log-parse-worker`。
8. 验证新日志上报只增加原始事件，不增加 pending 占位。
9. 用小范围真实条件验证任务创建、取消、续跑、筛选和统计。
10. 在生产同规格环境执行 10,000 条一分钟性能门禁。
11. 验证原始日志、解析统计和 CSV 导出小时筛选一致后投入生产。

## 14. 回滚

回滚时：

1. 停止 `sdk-log-parse-worker`；
2. 恢复旧 release 和前端；
3. 执行回滚辅助脚本，仅为新版本运行期间产生且没有任何解析结果的原始事件重建 `record_index=-1` pending 占位；
4. 重启旧 Admin 自动解析循环；
5. 验证 pending 开始下降且原始事件数量不变。

新增字段和索引不在紧急回滚中删除，避免破坏任务审计和延长恢复时间。

## 15. 测试与验收

### 15.1 后端

- 日志上报不创建 pending、不调用解析器；
- 时间边界覆盖同日、跨日、23 点结束、小时缺省和非法组合；
- 任务必须选择包名和完整时间范围，最大跨度 7 天；
- SDK 版本、设备 ID和日志级别精确过滤；
- 创建快照不追赶任务运行后的新日志；
- 当前解析器版本跳过、旧版本升级、强制重解析幂等；
- 200 条批次、3 进程结果合并和批量写入正确；
- 租约丢失、重启续跑、取消、连续超时和失败率门禁正确；
- 旧 `/reparse` 接口兼容；

### 15.2 前端

- 两个页面均显示开始/结束小时；
- 跨日连续范围请求参数正确；
- “查询结果”不创建任务；
- “开始解析”执行必填和 7 天限制；
- 状态、进度、速度、预计时间、失败和取消正确显示；
- 原始日志查看与 CSV 导出小时条件完全一致；

- 后端全量测试、前端全量测试和生产构建通过；

- 基准期间 SDK 上报和 Admin 健康检查无失败；
- 小时筛选在统计、明细、原始日志和导出中结果一致；
- 原始日志和历史解析结果数量不减少；

## 16. 监控与预警

- 任务运行超过按 166.67 条/秒计算目标的 120% 时预警；
- worker 心跳超过 30 秒未更新时预警；
- 连续超时达到 10 条或失败率超过 20% 时任务失败并告警；
- 4 核服务器 load 持续超过 2.5、CPU PSI 超过 5% 时预警；
- 可用内存低于 1 GiB或 Swap 持续超过 256 MiB时预警；
- 根盘使用率超过 70% 时预警、超过 80% 时严重告警；
- PostgreSQL 连接使用率超过 70% 时预警；
- `sdk_log_decodes` dead tuple 超过 15% 时检查 vacuum；
- 云套餐带宽需从 VPS 控制台补录，持续使用超过套餐 50% 时预警、超过 80% 时严重告警。
