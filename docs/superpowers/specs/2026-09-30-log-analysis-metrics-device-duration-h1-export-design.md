# 日志解析指标、设备时长与 H1 导出设计

> 日期：2026-09-30
> 基线：`f863887`
> 状态：设计已确认，待用户审阅正式规格
> 业务时区：`Asia/Shanghai`（UTC+8）

## 1. 背景

现有系统已具备原始日志保存、日志解析、基础解析统计、重解析任务、原始日志筛选与 CSV 导出，以及独立的 SDK 在线时长上报和管理端查询能力。但当前实现仍存在以下不足：

1. 日志上传后会进入默认解析链路，无法做到由管理员明确选择范围后再解析；
2. 当前解析器未正确识别同一 `extra` 内由 `||H1|` 连接的多条 H1，可能把多条声明合并为一条并由后续字段覆盖前序字段；
3. 现有持久化结构不足以高效、准确地统计 H1 声明及其中的逐次点击明细；
4. 缺少按 `config_id`（本项目视为 URL）聚合的计划、实际点击、响应成功、失败原因和插屏指标；
5. SDK 在线时长尚无符合业务口径的前端汇总与设备明细展示；
6. 原始日志导出不能选择只抽取 H1，同时不能在无 H1 时安全保留原始内容。

本设计将日志解析改为管理员显式创建的后置任务，建立结构化的 H1 声明事实和点击明细，并补充设备时长统计与 H1 混合导出。

## 2. 目标

1. SDK 日志上报只保存原始事件，不自动解析。
2. 管理员按包名和精确到小时的北京时间范围创建解析任务。
3. 每次任务重新解析并原子替换选定范围内的旧正式结果。
4. 一条原始日志中的每条 H1 独立成为声明记录，每条 `pa` 独立成为点击明细。
5. 统计支持按包名、连续时间范围和 `config_id` 维度查询。
6. 提供总体点击漏斗、目标类型分布、成功/失败占比、失败原因、`config_id` 占比和插屏指标。
7. 新增设备时长汇总与设备明细接口及页面。
8. 解析任务和设备时长页面默认最近 3 个北京时间自然日，允许修改；解析任务单次最多 7 天。
9. 原始日志导出增加 H1 模式：有 H1 时逐条拆行，无 H1 时保留原始 `extra`。
10. 10,000 条正常原始日志端到端解析不超过 60 秒。

## 3. 非目标

- 不修改 SDK 日志上报请求结构。
- 不要求 SDK 在 H1 内新增真实 URL；本项目直接使用 `config_id` 作为 URL 维度。
- 不将 H1 的 `duration_ms` 当作 SDK 在线时长。
- 不把同一设备的累计 `duration_s` 多次相加。
- 不引入 Redis、Kafka 或新的外部消息队列。
- 不删除 `sdk_events`、历史正式解析结果或现有在线时长记录。
- 不附带无关页面重构、认证改造或配置系统变更。

## 4. 已确认的术语和数据口径

### 4.1 URL 维度

`config_id` 就是本项目统计中的 URL。API 和前端可显示为“URL（config_id）”，数据库使用 `config_id` 分组，不反查真实 URL 字符串。

缺失 `config_id` 的 H1 归入“未知”，不得丢弃。

### 4.2 H1 声明与点击明细

- 一条 H1 代表一条日志声明；
- `p` / `expected_click_count` 是该 H1 的总计划点击数（排除插屏）；
- `pa` / `planned_click_attempts` 是逐次点击记录；
- `pa.did_click=true` 才计入实际实施点击；
- `pa.navigation_code=1` 才计入响应成功；
- 插屏统计独立计算，不混入上述非插屏点击漏斗。

`p` 与 `pa` 数量可能不一致。系统不得强行让两者相等：总计划数使用 `p`，按目标类型划分的计划数使用 `pa.target_kind`，并单独统计计划声明不一致的 H1 数量。

## 5. 总体架构

### 5.1 原始日志写入

```text
SDK POST /api/v1/log
  -> 校验请求
  -> 仅批量写入 sdk_events
  -> 提交事务
  -> 返回 accepted/rejected
```

写入链路不得创建解析占位、执行解析器或等待后台任务。解析失败不得影响原始日志入库。

### 5.2 显式后置解析

```text
管理员选择包名与 UTC+8 时间范围
  -> 创建解析任务并固定快照边界
  -> 独立 worker 按游标读取 sdk_events
  -> 从 extra 中提取全部 H1
  -> 每条 H1 生成声明暂存记录
  -> 每条 pa 生成点击暂存记录
  -> 分批提交并推进游标
  -> 全部成功后原子替换正式结果
  -> 标记任务 success
```

查询、分页、排序和页面刷新只读取正式结果，不得隐式创建任务。

### 5.3 正式结果和暂存结果

采用“声明事实表 + 点击明细表”方案：

- 正式 H1 声明表：一条 H1 一行；
- 正式点击明细表：一条 `pa` 一行；
- 任务 H1 暂存表：保存当前任务生成的声明；
- 任务点击暂存表：保存当前任务生成的点击；
- 解析任务表：保存范围、快照、游标、计数、状态和错误摘要。

暂存表必须以 `job_id` 隔离。任务成功前，页面不能读到暂存结果。

## 6. H1 抽取与解析规则

### 6.1 H1 边界识别

不得假设每条原始日志固定包含两条 H1。有几条就解析几条。

解析器识别：

- 字符串开头的 `H1|`；
- `||H1|` 后的新记录；
- 换行后的 `H1|`；
- Windows 和 Unix 换行；
- 单条 H1。

普通字段值中的 `||` 只有后续紧跟 `H1|` 时才是记录边界，避免误切文本。

H1 的 `record_index` 按其在单个原始 `extra` 中出现的顺序从 1 开始。

### 6.2 解析失败

- 单条 H1 失败只标记该条失败，不影响同一原始事件的其他 H1；
- 无 H1 的日志不生成正式 H1 声明；
- 任务统计分别记录原始事件数、H1 声明数、成功 H1 数、失败 H1 数和无 H1 事件数；
- 错误摘要不得包含完整 `extra`、Token、连接串或其他敏感信息。

### 6.3 解析器版本

本次必须升级解析器版本。正式声明和点击明细均记录 `decoder_version`，便于审计和后续重新解析。

## 7. 数据模型

### 7.1 H1 声明事实

建议新增 `sdk_log_h1_declarations`，核心字段：

| 字段 | 说明 |
|---|---|
| `event_id`、`event_server_ts`、`record_index` | 复合业务键 |
| `package_name`、`device_id`、`sdk_version` | 原始事件维度 |
| `config_id` | URL 维度，可空 |
| `window` | H1 窗口 |
| `declared_click_count` | `p` |
| `interstitial_presentation_count` | 插屏弹出次数，空按 0 聚合 |
| `interstitial_click_count` | 插屏非关闭点击次数，空按 0 聚合 |
| `interstitial_close_count` | 插屏关闭次数，空按 0 聚合 |
| `flow_duration_ms` | H1 流程耗时，仅用于流程分析 |
| `final_reason` | 流程结束原因 |
| `status`、`parse_error` | 解析状态和脱敏错误 |
| `decoder_version`、`parsed_at` | 解析审计 |
| `decoded_payload` | 必要的完整解析结果，供详情下钻 |

### 7.2 点击明细

建议新增 `sdk_log_click_attempts`，核心字段：

| 字段 | 说明 |
|---|---|
| H1 复合键 + `attempt_index` | 唯一定位点击 |
| `package_name`、`config_id`、`event_server_ts` | 高频查询维度冗余 |
| `target_kind` | `banner`、`anchored`、`web_element` 或其他 |
| `did_click` | 是否实际实施点击 |
| `navigation_code` | 响应结果代码 |
| `reason` | 解析后的失败原因 |
| `error_detail` | 原始错误详情的安全文本 |
| `navigation_result` | 响应结果说明 |
| `failure_category` | 按优先级固化的失败分类 |
| `click_timestamp` | 点击时间（如协议存在） |
| `page_context` | 首页或次级页面 |

### 7.3 暂存表

暂存表字段与正式表一致，并增加 `job_id`。暂存表按 `job_id` 建索引；任务完成或取消后按保留策略清理。

### 7.4 必要索引

至少支持：

- H1：`(package_name, event_server_ts, config_id)`；
- H1：`(event_id, event_server_ts, record_index)` 唯一键；
- 点击：`(package_name, event_server_ts, config_id, target_kind)`；
- 点击：H1 复合键 + `attempt_index` 唯一键；
- 暂存：`(job_id)` 和任务内业务键；
- 任务：`(status, created_at)`。

迁移必须幂等，不能删除原始日志或旧解析表。

## 8. 统计指标

所有指标使用同一组筛选条件：包名、北京时间连续范围，以及页面提供的其他精确筛选。总体和 `config_id` 明细必须复用同一查询构造器。

| 指标 | 计算方式 |
|---|---|
| 日志声明总数 | H1 声明行数 |
| 总计划点击数（非插屏） | `SUM(declared_click_count)`，空按 0 |
| 实际实施点击数（非插屏） | 点击明细中 `did_click=true` 的数量 |
| 响应成功数（非插屏） | 点击明细中 `navigation_code=1` 的数量 |
| 广告区域计划点击数 | `target_kind IN ('banner','anchored')` 的明细数量 |
| Banner 计划点击数 | `target_kind='banner'` 的明细数量 |
| Anchored 计划点击数 | `target_kind='anchored'` 的明细数量 |
| 网页元素计划点击数 | `target_kind='web_element'` 的明细数量 |
| 广告区域实际点击数 | 广告区域且 `did_click=true` |
| 广告区域响应成功数 | 广告区域且 `navigation_code=1` |
| 广告区域点击失败数 | 广告区域且 `navigation_code IS DISTINCT FROM 1` |
| 网页元素实际点击数 | 网页元素且 `did_click=true` |
| 网页元素响应成功数 | 网页元素且 `navigation_code=1` |
| 网页元素失败数 | 网页元素且 `navigation_code IS DISTINCT FROM 1` |
| 计划声明不一致数 | `declared_click_count != 点击明细数` 的 H1 数量 |
| 插屏弹出次数 | `SUM(interstitial_presentation_count)` |
| 插屏关闭成功占比 | 关闭数 / 弹出数 |
| 插屏非关闭点击占比 | 插屏点击数 / 弹出数 |

“实际实施点击”和“响应成功”是两个不同阶段，不能互相替代。

### 8.1 成功/失败占比

网页元素和广告区域均支持查看计划、实际点击、响应成功、失败数量及占比。占比必须明确分母，前端标签不得只显示含义不明的“成功率”。

响应成功/失败占比以该目标类型的点击明细总数为分母：

```text
成功占比 = navigation_code=1 数 / 该类型点击明细数
失败占比 = navigation_code!=1 数 / 该类型点击明细数
```

分母为 0 时显示 `-`。

### 8.2 失败原因分类

失败定义为 `navigation_code IS DISTINCT FROM 1`。分类优先级：

```text
reason -> error_detail -> navigation_result -> 未知原因
```

优先字段为空时才使用下一字段。汇总接口返回分类数量和占全部失败数的比例，并支持按目标类型和 `config_id` 下钻。

### 8.3 config_id 占比

```text
某 config_id 占比 = 该 config_id 的 H1 声明数 / 当前筛选范围全部 H1 声明数
```

缺失值归入“未知”。在无数据时占比显示 `-`；有数据时各组（含未知）合计应为 100%，仅允许前端小数舍入误差。

### 8.4 插屏指标

```text
关闭成功占比 = SUM(close_count) / SUM(presentation_count)
非关闭点击占比 = SUM(click_count) / SUM(presentation_count)
```

插屏弹出数为 0 时两项占比均为 `null`，前端显示 `-`，不得显示 `0%`。

## 9. 解析任务

### 9.1 默认范围和必填条件

前端进入页面时默认：

- 开始：北京时间前两天 `00:00`；
- 结束：北京时间今天 `23:59:59`。

即最近 3 个北京时间自然日。管理员可以修改，单次解析任务最大连续范围为 7 天。

创建任务必须提交：

- `package_name`；
- `date_from`、`hour_from`；
- `date_to`、`hour_to`。

小时范围使用连续区间而非每天重复区间。例如 9 月 20 日 08 时至 9 月 22 日 17 时表示：

```text
[2026-09-20 08:00:00+08:00, 2026-09-22 18:00:00+08:00)
```

后端统一转换成 UTC 半开区间。

### 9.2 快照与覆盖策略

任务创建时固化：

```text
snapshot_end = min(请求范围结束, 任务创建时刻)
```

任务不追赶创建后新到日志。每次任务都重新解析范围内所有匹配原始日志，不跳过已有结果，不提供默认跳过模式。

### 9.3 执行与替换

- 全局同时只运行一个解析任务；
- 默认每批读取 200 条原始事件；
- 最多 3 个独立解析进程；
- 每批写入暂存表并独立提交，同时更新稳定游标；
- 全部处理完成后，在一个事务中删除所选包名与时间范围的旧正式结果，并导入本任务暂存结果；
- 失败或取消不触碰现有正式结果，只清理或标记暂存数据；
- 服务重启后从最后成功批次游标继续。

游标使用 `(server_ts, event_id)`，不得只用自增 ID 推断时间顺序。

### 9.4 状态和进度

```text
pending -> running -> success | failed | cancelled
```

进度至少包括：目标原始事件数、已处理事件数、H1 声明数、解析失败 H1 数、无 H1 事件数、速度、预计剩余时间、开始/结束时间和脱敏错误摘要。

### 9.5 异常保护

- 单条解析超时只失败该条；
- 连续 10 条超时则任务失败；
- 至少处理 100 条后，总失败率超过 20% 则任务失败；
- 取消在当前批次提交后生效；
- 租约和心跳防止多个 worker 同时执行同一任务。

## 10. 解析统计 API

应提供或扩展以下能力：

- 创建、查询、取消解析任务；
- 查询解析覆盖和任务进度；
- 查询总体统计；
- 按 `config_id` 查询统计明细；
- 查询网页元素和广告区域成功/失败维度；
- 查询失败原因分类；
- 下钻到 H1 声明和点击明细。

所有统计接口统一支持 `package_name/date_from/hour_from/date_to/hour_to`，使用 UTC+8 连续范围。排序字段使用白名单，分页在数据库完成。

## 11. 设备时长接口与口径

### 11.1 数据来源

只使用 `sdk_usage_durations.duration_s`。H1 的 `flow_duration_ms` 是流程执行耗时，不参与设备在线时长统计。

SDK 当前上报的是设备累计值，因此同一设备在筛选范围内只取 `server_ts` 最新的一条记录。不得对同一设备的多次上报求和。

### 11.2 筛选与默认值

设备时长使用：

- 可选包名；不选时查询全部包名；
- 开始日期/小时；
- 结束日期/小时；
- UTC+8 连续范围；
- 默认最近 3 个北京时间自然日。

### 11.3 汇总定义

按“包名 + 机型”汇总：

```text
设备数 = 具有范围内记录的唯一 device_id 数
汇总时长 = 每台设备最新 duration_s 之和
平均时长 = 汇总时长 / 设备数
```

平均时长保留整数秒，舍入规则由后端统一定义为四舍五入到最近整数秒。设备数为 0 时平均时长为 `null`。

### 11.4 时长分布

每台设备以其最新 `duration_s` 落入一个且仅一个区间：

| 区间 | 条件 |
|---|---|
| 5 分钟以内 | `duration_s <= 300` |
| 5～10 分钟 | `300 < duration_s <= 600` |
| 10～15 分钟 | `600 < duration_s < 900` |
| 15 分钟以上 | `duration_s >= 900` |

每档返回设备数和占该“包名 + 机型”设备总数的比例。四档设备数之和必须等于设备数。

### 11.5 API

```http
GET /api/admin/usage-durations/summary
GET /api/admin/usage-durations/devices
```

`summary` 返回包名、机型、设备数、汇总时长、平均时长、四档分布及最后上报时间。

`devices` 用于展开某个包名和机型，返回设备 ID、最新时长、SDK 版本、应用版本和最后上报时间。去重和最新记录选择必须由数据库窗口函数或等价 SQL 完成，不在前端去重。

## 12. H1 混合导出

### 12.1 请求

现有日志导出请求新增：

```json
{
  "export_mode": "raw | h1"
}
```

默认 `raw`，保持现有兼容行为。`h1` 表示 H1 混合导出。

### 12.2 CSV 列

```text
event_id,server_time,package_name,device_id,device_model,os,ver,
sdk_version,level,record_type,record_index,content
```

### 12.3 导出规则

- 包含 H1：每条 H1 输出一行，`record_type=h1`，`record_index` 从 1 开始，`content` 为完整 H1 原文；
- 没有任何 H1：输出一行，`record_type=raw`，`record_index` 为空，`content` 为原始 `extra`；
- 不假设每条日志只有两条 H1；
- H1 抽取复用与解析器相同的边界识别函数，但只做文本拆分，不依赖解析任务是否完成；
- 导出不得因为某条内容无法解析而漏掉该原始日志；
- CSV 必须正确转义换行、双引号、逗号和公式注入前缀；
- 导出与原始日志页面严格复用已应用的包名、日期、小时、SDK 版本、设备 ID和日志级别筛选。

## 13. 前端设计

日志模块包含三个页签。

### 13.1 解析统计

筛选栏：包名、开始日期/小时、结束日期/小时，默认最近 3 天。

操作：查询已有结果、开始解析、取消任务、重置。查询不得触发解析。

页面内容：

1. 任务进度卡；
2. 总体指标卡；
3. `config_id`（URL）统计表和占比；

## 14. 性能要求

在与生产相同的 4 vCPU 环境，使用真实结构的脱敏样本验证：

- 10,000 条正常原始日志从任务开始到正式结果替换完成不超过 60 秒；
- 计时包括数据库读取、进程间传输、H1 拆分、解析、点击明细生成、暂存写入、最终替换和任务更新；
- 基准期间 SDK 日志上报和 Admin 健康接口持续成功；
- 不通过无限增加并发规避瓶颈；并发上限为 3；
- 设备时长汇总和统计查询必须在数据库聚合，不把全量明细拉到前端。

## 15. 测试与验收

### 15.1 H1 解析

- 单条 H1；
- `||H1|` 多条记录；
- 换行多条记录；
- Windows/Unix 换行；
- 字段值中普通 `||` 不误切；
- 无 H1；
- 一条原始事件产生任意数量 H1；
- 前一条 H1 不被后一条字段覆盖。

### 15.2 指标

- H1 声明总数准确；
- `p`、`pa.did_click`、`navigation_code` 三套口径互不混用；
- Banner、Anchored、网页元素分类正确；
- 广告区域为 Banner + Anchored；
- 失败原因优先级正确；
- `config_id` 占比含未知组且合计为 100%；
- 插屏分母为 0 时返回 `null`；
- `p` 与 `pa` 不一致时指标保持各自口径并产生质量提示。

### 15.3 任务

- 默认最近 3 天；
- 可修改且最大 7 天；
- UTC+8 同日、跨日和 23 点边界；
- 创建时快照；
- 每次重解析全范围；
- 暂存与原子替换；
- 失败、取消、重启续跑不污染正式结果；
- 全局单任务、租约和心跳。

### 15.4 设备时长

- 每设备仅取范围内最新记录；
- 包名 + 机型汇总正确；
- 汇总时长不重复累加同设备历史记录；
- 平均时长等于汇总时长除设备数；
- 300、600、900 秒边界准确归类；
- 四档设备数之和等于总设备数；
- 展开设备明细与汇总来源一致。

### 15.5 导出

- H1 每条独立一行；
- 无 H1 时保留原始 `extra`；
- 混合数据不漏行；
- 元数据列正确；
- CSV 转义和公式注入保护；
- 查看与导出的包名、日期、小时、SDK、设备和级别筛选一致。

### 15.6 全量门禁

- 后端全量测试通过；
- 前端全量测试和生产构建通过；
- 数据库迁移重复执行安全；
- 10,000 条正常日志端到端解析不超过 60 秒；
- 原始日志和在线时长历史记录数量不减少。

## 16. 部署与回滚

部署前备份：

- PostgreSQL 数据库；
- 当前 release；
- 前端 dist；
- systemd 配置；
- 宝塔 Nginx 配置。

部署顺序：迁移数据库、部署 API、部署独立解析 worker、部署前端，以单包名和一小时范围做小规模验收，再执行性能门禁。

回滚时停止新 worker，恢复旧 release 和前端。新增表和字段保留，不在紧急回滚中删除；原始日志未改变。旧解析链路如需恢复，必须按旧版本需要重建其占位数据，并验证原始事件数量不变。
