# 日志分析生效范围、正式结果与包级在线时长设计

> 日期：2026-10-08  
> 基线：`d08718c`  
> 分支：`codex/log-analysis-scope-package-usage-20261008`  
> 状态：规格与实施计划待审查，当前不实施、不部署  
> 业务时区：`Asia/Shanghai`（UTC+8）

## 1. 背景与问题定义

当前日志分析页同时存在两条容易混淆的结果链路：

1. 旧汇总接口使用 `SdkEvent` 左连接 `LogDecode`，可以显示原始事件数量，但无法代表显式解析任务发布的正式 H1/click 事实；
2. 新解析任务链路已经具备任务快照、暂存结果和正式发布表，但主页面仍展示旧 `LogDecode` 聚合，导致原始事件有数据而正式指标为 0 时难以判断真实含义；
3. 查询和刷新没有完全复用同一个前端生效范围。刷新事件虽然带有最新表单快照，但页面处理函数会回读旧状态，日期、小时或包名可能因此回退；旧 summary 请求也未传递小时；
4. 在线时长的设备级最新值选择已经存在，但汇总仍按包名和机型分组，不能直接得到“一包一行”的业务结果；
5. 旧时长说明文档没有明确强调 `duration_s` 是该设备在报告时的累计时长，不能把同一设备的历史报告重复相加。

本规格不新增一条自动解析链路，而是把现有显式解析链路、正式结果表和在线时长汇总统一到一个可审计的范围模型下。

## 2. 目标

### 2.1 必须达成

1. 查询、刷新、解析任务创建、解析任务结果刷新和在线时长查询均使用同一个“生效范围”。
2. 生效范围使用包名、北京时间开始日期/小时、北京时间结束日期/小时；初始默认仅为最近 3 个北京时间自然日，仍允许选择最多 7 个日历日。
3. 查询和刷新只读已有结果，绝不隐式创建或启动解析任务；只有用户明确点击解析按钮时才创建任务。
4. 日志分析主结果以显式解析任务成功发布的 H1 声明和 click 明细正式表为准，旧 `LogDecode` 聚合不得继续作为主指标来源。
5. 页面明确区分：尚未查询/未选择包名、当前范围无解析任务、任务排队中/运行中、任务失败/取消、任务成功但正式结果为 0、任务成功且有正式结果。
6. 成功解析后，只刷新创建该任务时的同一生效范围，并展示任务快照边界和发布结果，不把任务完成时间之后新到达的日志误计入该任务。
7. 在线时长汇总每个包名一行：范围内每台设备取最新报告，汇总累计时长总和、去重设备数、平均时长、四个时长桶的数量和占比，以及最大最后上报时间。
8. 在线时长默认页面不展示按设备或机型拆分的汇总行；必要的设备明细接口保留兼容能力，并改为显式下钻能力。
9. 更新旧时长定义文档，使“累计时长 + 范围内每设备最新报告”的现行口径成为唯一说明。

### 2.2 非目标

- 不修改 SDK 日志上传协议、原始事件写入协议或客户端上报行为。
- 不恢复或新增上传后自动解析、定时自动解析、查询触发解析。
- 不删除 `sdk_events`、`LogDecode`、历史正式 H1/click 表或旧 API；兼容接口可继续保留，但不再作为主页面口径。
- 不对历史正式结果做全量回填，不自动重跑生产解析任务，不在本变更中清理旧表或旧数据。
- 不改变分区维护、SDK 上传协议、配置系统或旧 8102 相关范围。
- 不把 H1 的 `flow_duration_ms` 当作 SDK 在线时长。

## 3. 术语与规范化范围

### 3.1 `AppliedAnalysisScope`

前端和后端都以规范化后的生效范围作为请求边界：

```text
package_name: 非空、完全匹配的包名
date_from: 北京时间开始日期
hour_from: 北京时间开始小时，0–23
date_to: 北京时间结束日期
hour_to: 北京时间结束小时，0–23，含该小时
```

范围通过现有 `business_hour_utc_range` 转换为 UTC 半开区间 `[start_utc, end_utc)`。例如 `2026-10-08 09:00` 到 `2026-10-08 11:00` 表示包含 09:00、10:00、11:00 整三个北京时间小时，结束边界为 12:00。

UI 的“最近 3 天”必须按北京时间自然日计算，而不是按浏览器本地时区或最近 72 小时计算。7 天限制仍按开始日期到结束日期的日历差校验；同日小时范围必须满足结束边界不早于开始边界。

### 3.2 初始范围、草稿范围和生效范围

- **初始范围**：页面首次打开时由北京时间当天计算最近 3 个自然日，并填入表单草稿；默认不发起解析任务。
- **草稿范围**：用户正在修改但尚未点击查询或刷新时的表单值；不能用于结果请求。
- **生效范围**：用户点击“查询已有结果”或“刷新”后，经校验并由页面状态保存的快照；所有结果、任务和刷新请求必须使用它。
- **任务范围**：创建解析任务时持久化的生效范围副本；任务运行期间不可被后续表单修改影响。

查询和刷新必须接收并应用组件发出的完整范围快照，不能通过闭包或旧 `appliedFilters` 回读替代。重置只重置表单和生效范围到初始最近 3 天值，不启动解析。

## 4. 日志分析主结果设计

### 4.1 查询、刷新与显式解析

页面操作契约如下：

| 操作 | 是否更新生效范围 | 是否读取已有正式结果 | 是否创建解析任务 |
|---|---:|---:|---:|
| 查询已有结果 | 是 | 是 | 否 |
| 刷新 | 是 | 是 | 否 |
| 重置 | 是，恢复初始范围 | 按页面现有约定重新加载空/默认状态 | 否 |
| 明确点击解析 | 使用当前生效范围 | 创建后轮询该任务 | 是 |
| 解析成功 | 保持任务范围 | 刷新同一任务范围 | 否（不重复创建） |

刷新不能借机解析，页面挂载、切换范围、打开指标面板、轮询任务状态也不能隐式创建解析任务。

### 4.2 正式结果作为主路径

主分析结果必须读取显式任务成功发布的正式表：

- H1 声明指标来自 `sdk_log_h1_declarations`；
- click 指标、目标类型、成功/失败和失败原因来自 `sdk_log_click_attempts`；
- 任务范围、快照边界、状态和计数来自 `sdk_log_reparse_jobs`；
- 任务未成功发布时，不得读取该任务的暂存表作为页面正式结果。

现有 `LogMetricsPanel` 的正式指标、配置/目标/失败原因/H1 下钻能力应继续复用并补充任务状态和范围展示。主视图不再把旧 summary 表中的 `LogDecode` 字段（例如 flow、plan、actual、failed）呈现为正式 H1 指标。

为保留用户已配置的包资料、必要的指标配置和兼容排查能力，旧 summary/API 可在次级的“原始事件兼容汇总”区域保留，但必须：

- 明确标注数据来源为 `SdkEvent + LogDecode`；
- 不与正式 H1/click 结果使用相同的主标题、颜色或指标标签；
- 不作为解析任务成功/失败的判定依据；
- 不阻塞或改变正式结果刷新；
- 后续可独立下线，不影响正式表查询。

如果现有包资料编辑和列配置只依附于旧 summary 表，实施时应将其移入包资料/指标配置区或兼容汇总区，保留已存配置和编辑行为，不得因移除主路径而丢失配置。

### 4.3 任务状态和空值语义

主页面显示以下互斥状态，并给出明确文案：

| 状态 | 判定 | 页面含义 |
|---|---|---|
| `scope_required` | 包名或范围尚未提交 | 请先查询已有结果或刷新 |
| `no_job` | 生效范围内无任务 | 尚未对该范围执行显式解析；原始事件数量不等于正式结果 |
| `pending/running` | 有未完成任务 | 展示任务快照范围、进度和预计等待，不展示暂存为正式结果 |
| `failed/cancelled` | 最新任务未成功 | 展示失败/取消原因和重试入口，旧成功任务是否可见必须按明确的“最近一次成功任务”规则处理 |
| `success_empty` | 任务成功且正式 H1/click 行数为 0 | 明确为“任务已完成，范围内没有可发布的正式 H1/click”，不能显示为加载中或接口异常 |
| `success_non_empty` | 任务成功且有正式结果 | 展示正式 H1/click 指标和任务发布摘要 |

“成功但 0 行”还应提供任务计数：扫描原始事件数、H1 数、click 数、无 H1 事件数和失败 H1 数（已有字段则复用）。这样可以区分真实无 H1、范围内没有源事件和解析失败。

### 4.4 解析任务快照语义

创建任务时固定：

- 用户选择的北京时间范围及其 UTC 转换边界；
- `snapshot_end = min(range_end, create_time)`；
- 任务查询只处理 `server_ts >= range_start AND server_ts < snapshot_end` 的原始事件。

任务创建后晚于 `snapshot_end` 到达的日志不属于本任务，即使仍落在用户选择的日期/小时范围内，也必须通过新的显式解析任务纳入。任务详情和页面文案必须展示 `snapshot_end`，避免用户把“本范围尚未被任务扫描到”误认为“正式解析漏数”。

任务成功只表示该任务快照已完整发布，不表示该包在当前范围内未来不会有更多日志。

## 5. 在线时长汇总设计

### 5.1 数据口径

`sdk_usage_durations.duration_s` 是设备在该条报告中的累计在线时长。对于所选范围内每个 `(package_name, device_id)`，按 `server_ts DESC, id DESC` 选取最新报告一条；之后只对这些最新报告聚合，不把同一设备的历史报告相加。

包级汇总每个 `package_name` 一行，字段至少包括：

| 字段 | 计算 |
|---|---|
| `package_name` | 包名 |
| `device_count` | 最新报告中的去重设备数 |
| `total_duration_s` | 最新报告 `duration_s` 之和 |
| `average_duration_s` | `total_duration_s / device_count`，无设备为 `null` |
| 四个桶数量 | 按最新累计时长划分的设备数 |
| 四个桶占比 | 对应桶数量 / `device_count`，无设备为 `null` |
| `last_report_at` | 最新报告时间的最大值 |
| `last_report_at` 的包级时区展示 | 统一按北京时间展示，原始 API 时间仍保持可解析的时区信息 |

四个桶必须继续复用当前产品定义和边界，实施前在服务常量与测试中固定名称、左右边界和包含关系；本次不改变桶的业务含义，只改变汇总粒度和输入集合。

### 5.2 API 和页面

- summary API 默认只返回包级行，不再按 `device_model` 分组；排序字段不能要求依赖机型分组。
- 设备明细 API 继续支持旧 `device_model` 参数，以兼容既有调用；新增/保留无机型参数时返回包内全部设备，且明确是下钻接口。
- 页面行键改为当前范围加包名，不得继续使用包名加机型。
- 页面默认只渲染包级汇总，不展示单设备列表或机型汇总行；用户明确展开详情时才调用兼容的 devices 接口。
- 设备详情可继续展示机型、设备 ID、最新累计时长和最后上报时间，但这些明细不参与默认汇总表。

## 6. 兼容性与迁移判断

### 6.1 数据库

本变更不需要新增表或数据回填：正式 H1/click 表、解析任务表和在线时长表已经存在。除非实施阶段发现现有字段不足，否则不创建数据库迁移；不得删除旧表、旧索引或历史结果。

### 6.2 API

- 新的正式结果查询继续使用现有 metrics/parse-job API，并补齐统一范围和任务状态返回；如果需要增加字段，采用向后兼容的可选字段。
- 旧 summary/detail API 继续保留，给历史调用方和兼容区使用，但主页面不得依赖其 `LogDecode` 指标。
- usage summary 的响应从“包名 + 机型”收敛到“包名一行”。这属于主 UI 目标契约，必须同步更新前端类型和测试；设备 detail API 的旧机型过滤参数保留。

### 6.3 配置和历史资料

不修改配置系统，不迁移或清空已有包资料、指标配置和列设置。若需要改变前端保存位置，只做兼容读取和渐进写入，不在本次引入数据清理。

## 7. 验收标准

1. 页面首次打开显示最近 3 个北京时间自然日；不发起 POST 解析任务。
2. 任意修改日期、开始/结束小时和包名后点击刷新，实际请求与当前表单快照一致；小时范围不会丢失。
3. 超过 7 个日历日、空包名、结束早于开始的范围被前端拒绝，后端也拒绝非法范围。
4. 点击查询、刷新、切换页面和轮询不会创建解析任务；只有明确点击解析才有一次 POST。
5. 解析任务的范围和 `snapshot_end` 在详情和结果区可见；任务完成后刷新仍使用同一任务范围。
6. 主结果的正式 H1/click 数值与正式表查询一致；无正式任务时不会用 `LogDecode` 聚合冒充正式结果。
7. 页面可区分无任务、运行中、失败、成功空结果和成功有结果；成功空结果不会显示为异常或“正在解析”。
8. 一条包内包含多个机型时，usage summary 仍只返回一行；该行的总时长等于范围内每台设备最新累计值之和。
9. 同一设备有多条历史报告时只计最新一条；机型变化不产生重复设备。
10. usage 默认页面不渲染设备级行；显式下钻仍可调用兼容的设备明细接口。
11. `docs/48-SDK-USAGE-DURATION-DESIGN-20260929.md` 更新为当前累计/最新设备报告口径，并明确禁止历史报告重复相加。
12. 本变更不产生数据库迁移、生产解析任务或部署动作；回滚只需恢复应用版本。

## 8. 发布与回滚

### 发布前

- 先完成本规格和实施计划审查，再实施代码；
- 运行后端范围、正式结果、解析快照和 usage 聚合测试；
- 运行前端组件、参数契约和生产构建测试；
- 检查 `git diff --check`、类型检查、构建产物和未触碰的保护范围；
- 不在发布前自动创建生产解析任务，不对生产数据做回填。

### 发布

后端 API、前端主视图和类型契约必须作为同一应用版本发布。因无数据库迁移，发布顺序不要求执行 SQL；发布后只做只读范围验证和页面行为验证。

### 回滚

若主结果、范围参数或 usage 汇总出现回归，直接回滚到发布前应用版本。由于不删除表、不改变历史数据、不创建生产任务，回滚不需要数据库逆迁移；旧兼容 API 和历史正式结果仍可继续读取。
