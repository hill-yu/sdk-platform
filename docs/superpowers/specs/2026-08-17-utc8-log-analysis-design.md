# UTC+8 时间统一与日志解析统计设计

> 日期：2026-08-17
>
> 状态：待实施
>
> 适用范围：SDK API、Admin API、管理后台、PostgreSQL 统计与历史日志解析

## 1. 背景与目标

当前系统以 UTC 保存和返回时间，管理后台日志页面直接展示 UTC 时间，日期筛选和部分统计也按 UTC 自然日计算。日志 `payload.extra` 保存的是原始流程字符串，前端只能查看原文；项目外已有 `flow_log_decoder.py`，但尚未接入后台。日志筛选后端使用完全匹配并已实际生效，用户感知异常主要来自日期边界仍按 UTC，以及页面缺少明确的生效条件反馈。

本次目标：

1. 数据库继续安全保存绝对时间，所有业务日期统一按 `Asia/Shanghai`（UTC+8）解释、统计和展示；
2. 保留包名、设备 ID 和日志级别的完全匹配筛选，修正北京时间日期边界；
3. 将 `flow_log_decoder.py` 的 `extra` 解析能力整理为后端受控模块，保留原始日志并持久化结构化结果；
4. 提供“日期 + 包名”聚合页、逐条解析明细和原始日志追溯；
5. 支持后台维护包名对应的别名、公司和账户；未配置时显示为空；
6. 支持全局增删、排序聚合表中的可见指标列，内置指标数据不被物理删除。

不在本次范围内：

- 不把 PostgreSQL 中的历史时间值整体加八小时；
- 不把服务器或 PostgreSQL 系统时区作为业务时区实现手段；
- 不改 SDK 日志上传协议，不要求 SDK 上传解析后的内容；
- 不允许管理员编写任意指标公式；
- 不把包名、设备 ID 改为模糊匹配；
- 不删除或覆盖 `payload.extra` 原文。

## 2. 核心决策

### 2.1 时间存储与业务时区分离

PostgreSQL `TIMESTAMPTZ`、服务端内部时间和 SDK 客户端时间继续表示绝对时刻。业务时区固定为 IANA 时区 `Asia/Shanghai`，不得仅使用固定字符串拼接或对所有时间机械加八小时。

API 对外返回的时间统一序列化为带偏移量的 ISO 8601：

```text
2026-08-17T16:30:00+08:00
```

日期参数表示北京时间自然日。例如：

```text
date_from=2026-08-17
date_to=2026-08-17
```

对应数据库查询半开区间：

```text
[2026-08-16T16:00:00Z, 2026-08-17T16:00:00Z)
```

半开区间避免结束时间精度、闰秒和重复计数问题。

### 2.2 解析结果独立持久化

采用“原始事件 + 独立解析结果”模型。SDK 日志先正常写入 `sdk_events`，随后解析 `payload.extra` 并写入解析结果表。原始日志是事实来源，解析结果是可重建的派生数据。

解析失败不能导致整批日志上报失败；失败记录必须保留解析状态、解析器版本和脱敏错误，不记录完整原始字符串到错误日志。

### 2.3 两层日志分析页面

默认展示按“北京时间日期 + 包名”聚合的数据表。点击聚合行进入该分组的逐条解析明细，再点击明细查看完整结构化 JSON 与原始 `extra`。原有原始日志视图保留。

### 2.4 全局列配置

列配置为全局配置，由当前 Admin Token 权限维护，所有管理员看到同一套显示列和顺序。系统内置指标只能显示、隐藏、排序和恢复默认，不能物理删除或修改计算口径。

## 3. 总体架构

```text
SDK POST /api/v1/log
        |
        v
写入 sdk_events（原始 payload.extra 永久保留）
        |
        v
FlowLogDecoder（受控 Python 模块）
        |
        +--> 成功：写入结构化字段 + decoded_payload
        |
        +--> 失败：写入 failed + 脱敏错误

Admin API
  +--> 聚合查询（北京时间日期 + 包名）
  +--> 解析明细查询
  +--> 原始日志追溯
  +--> 包名资料配置
  +--> 全局列配置
  +--> 受限历史重解析
```

解析写入需与日志接收解耦。首期可以在日志批次提交成功后执行受限的后台任务；不得让单条解析耗时无限延长 SDK 请求。生产实现必须有最大 `extra` 长度、单批数量和执行超时。

## 4. 时间统一设计

### 4.1 统一工具

后端新增集中式时间工具，至少提供：

- `BUSINESS_TIMEZONE = ZoneInfo("Asia/Shanghai")`；
- 将任意有时区时间转换为北京时间；
- 将北京时间日期转换为 UTC 查询边界；
- 统一序列化为 `+08:00` ISO 8601；
- 获取北京时间的今日、昨日和小时边界。

禁止业务代码继续散落使用 `date.today()` 作为业务日期，也禁止对数据库时间直接 `+ timedelta(hours=8)` 后再当作无时区时间使用。

### 4.2 API 时间字段

下列现有字段及后续新增时间字段统一返回 UTC+8：

- `server_ts`、`client_ts`；
- `created_at`、`updated_at`、`publish_at`；
- Dashboard 趋势点时间；
- 日志解析时间、重解析时间；
- 包名资料与列配置更新时间。

内部排序、版本判断、超时确认继续比较绝对时间，不比较格式化字符串。

### 4.3 统计与物化视图

所有“今日/昨日/按日/按小时”统计以北京时间划分。PostgreSQL 表达式应明确指定时区，例如：

```sql
(server_ts AT TIME ZONE 'Asia/Shanghai')::date
date_trunc('hour', server_ts AT TIME ZONE 'Asia/Shanghai')
```

现有按 UTC 构建的日、小时物化视图需要安全重建或替换。迁移前后核对原始事件总数；重建物化视图不得修改 `sdk_events`。

## 5. 解析模块设计

### 5.1 来源与边界

解析逻辑以用户提供的 `flow_log_decoder.py` 为行为基线，只接收 `payload.extra` 字符串，不读取任意文件、不执行命令、不导出 Excel、不使用其 CLI 输入路径能力。

接入时拆分为：

- 纯解析核心：字符串输入，结构化对象输出；
- 映射词库：字段代码、枚举和中文展示映射；
- 聚合投影：从完整结构化对象提取数据库关键字段；
- 解析器版本常量；
- 独立测试向量。

CLI、XLSX、文件系统默认路径和标准输入逻辑不进入在线服务。

### 5.2 支持格式

保持脚本已有行为：

- `H1|...` 紧凑流程日志；
- `FINAL_HOST_FLOW_RESULT`；
- 旧版 `FINAL_FLOW_RESULT`；
- 脚本已支持的样本行和可读格式。

一个 `extra` 可能包含多条可解析记录。解析结果表以“原始事件 + 记录序号”区分，不能假设每个事件只产生一条解析记录。

### 5.3 解析状态

状态枚举：

- `pending`：原始日志已写入，等待解析；
- `success`：至少得到一条支持的解析记录；
- `unsupported`：内容合法但没有支持的记录；
- `failed`：解析器异常或输入违反限制。

失败信息只保存异常类型和受限长度的安全摘要，不保存 Token、完整 `extra`、数据库连接信息或堆栈到 API 响应。

### 5.4 解析器版本

每条结果保存 `decoder_version`。词库或解析算法升级后，历史任务按版本筛选重解析。重解析使用 upsert，键保持稳定，必须能够重复执行且结果一致。

## 6. 数据模型

### 6.1 `sdk_log_decodes`

建议字段：

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `event_id` | BIGINT | 原始事件 ID |
| `event_server_ts` | TIMESTAMPTZ | 原始事件分区键的一部分 |
| `record_index` | INTEGER | 同一 `extra` 中的解析记录序号，从 0 开始 |
| `package_name` | VARCHAR(255) | 冗余查询维度，非空 |
| `device_id` | VARCHAR(64) | 可空 |
| `status` | VARCHAR(32) | pending/success/unsupported/failed |
| `decoder_version` | VARCHAR(32) | 非空 |
| `decoded_timestamp` | TIMESTAMPTZ | 解析日志内部时间，可空 |
| `url` | TEXT | 解析 URL/URL 别名，可空 |
| `config_id` | INTEGER | 可空 |
| `window` | VARCHAR(32) | 可空 |
| `expected_click_count` | INTEGER | 可空 |
| `actual_click_count` | INTEGER | 可空 |
| `ad_click_count` | INTEGER | 可空 |
| `interstitial_presentation_count` | INTEGER | 可空 |
| `interstitial_click_count` | INTEGER | 可空 |
| `interstitial_close_count` | INTEGER | 可空 |
| `duration_ms` | BIGINT | 可空 |
| `final_reason` | VARCHAR(128) | 可空 |
| `is_success` | BOOLEAN | 可空，无法判定时不伪造 false |
| `decoded_payload` | JSONB | 完整结构化结果 |
| `parse_error` | VARCHAR(512) | 脱敏错误，可空 |
| `parsed_at` | TIMESTAMPTZ | 非空 |

主键或唯一键使用：

```text
(event_id, event_server_ts, record_index)
```

至少建立以下索引：

- `(package_name, event_server_ts DESC)`；
- `(status, event_server_ts DESC)`；
- `(decoder_version, status)`；
- `(event_id, event_server_ts)`。

外键若受分区表约束无法稳定建立，可由迁移校验和服务层保证引用一致；不得为了建立外键重写原始事件主键。

### 6.2 `sdk_package_profiles`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `package_name` | VARCHAR(255) | 主键，沿用包名规范化规则 |
| `alias` | VARCHAR(255) | 可空 |
| `company` | VARCHAR(255) | 可空 |
| `account` | VARCHAR(255) | 可空 |
| `created_at` | TIMESTAMPTZ | 非空 |
| `updated_at` | TIMESTAMPTZ | 非空 |

API 输出时将未配置或 NULL 的三个资料字段统一展示为空字符串，但数据库仍允许 NULL，用于区分未配置状态。页面直接编辑时执行 upsert。

### 6.3 `sdk_admin_preferences`

首期只保存一条日志列全局配置：

| 字段 | 类型 | 说明 |
|---|---|---|
| `preference_key` | VARCHAR(128) | 主键，固定 `log_analysis_columns` |
| `value` | JSONB | 有序列 ID 数组 |
| `updated_at` | TIMESTAMPTZ | 非空 |

仅接受后端白名单中的列 ID；拒绝未知 ID、重复 ID、空列表和超过列总数的配置。

## 7. 聚合指标口径

聚合键为“北京时间日期 + package_name”。包名资料不参与聚合键。

| 指标 | 口径 |
|---|---|
| 日期 | `event_server_ts` 按 Asia/Shanghai 转换后的日期 |
| 包名 | 原始事件 `package_name` |
| 别名/公司/账户 | 左连接包名资料；未配置显示空 |
| 网页 URL | 分组内 URL；存在多个时返回主 URL 并标识数量，明细可查看全部 |
| 用户数 | 去重非空 `device_id` |
| 流程日志数 | `status=success` 的解析记录数 |
| 计划点击数 | 有效 `expected_click_count` 合计 |
| 实际点击数 | 解析出的已执行点击尝试合计 |
| 广告区域点击数 | 解析器判定为广告目标的点击尝试合计 |
| 插屏展示数 | 有效 `interstitial_presentation_count` 合计 |
| 插屏点击数 | 有效 `interstitial_click_count` 合计 |
| 平均流程耗时 | 有效 `duration_ms` 的平均值 |
| 成功完成率 | `is_success=true` 数量 / `is_success` 非空数量 |
| 解析失败数 | failed + unsupported 的原始日志/记录数量，响应分别保留子计数 |

计数缺失可以在求和时按零贡献，但 API 需同时返回有效样本数。平均值和比例只使用有效数据，不能把缺失值伪造为零。除零时返回 `null`，前端显示 `-`。

## 8. Admin API 设计

所有接口沿用：

```http
Authorization: Bearer <ADMIN_TOKEN>
```

### 8.1 聚合查询

```http
GET /api/admin/log-analysis/summary
```

查询参数：

- `date_from`、`date_to`：北京时间日期，默认最近 7 个自然日；
- `package_name`：完全匹配；
- `device_id`：完全匹配；
- `log_level`：debug/info/warn/error；
- `page`、`page_size`；
- `sort_by`、`sort_order`：仅允许白名单列。

响应每项包含聚合指标、有效样本数和包名资料。日期范围设最大跨度，防止全表无限聚合。

### 8.2 解析明细

```http
GET /api/admin/log-analysis/details
```

必须携带聚合分组的 `date` 和 `package_name`，支持设备、级别、解析状态和分页筛选。时间字段返回 `+08:00`。

### 8.3 单条详情

```http
GET /api/admin/log-analysis/details/{event_id}?event_server_ts=<ISO8601>&record_index=0
```

由于事件 ID 在分区表语义下不能单独作为稳定键，必须同时传事件时间和记录序号。响应包含完整 `decoded_payload` 与原始 `extra`。原始日志只在这个受 Admin 鉴权的详情接口返回。

### 8.4 包名资料

```http
GET /api/admin/package-profiles?package_name=<exact>
PUT /api/admin/package-profiles/{package_name}
```

更新请求：

```json
{
  "alias": "",
  "company": "",
  "account": ""
}
```

空字符串规范化为 NULL；响应仍返回空字符串。沿用已有包名标准化与长度限制。

### 8.5 全局列配置

```http
GET /api/admin/log-analysis/columns
PUT /api/admin/log-analysis/columns
```

更新请求：

```json
{
  "columns": ["date", "package_name", "alias", "user_count", "flow_count"]
}
```

后端返回完整列目录、默认配置和当前全局配置。前端不能自行保存未知列。

### 8.6 历史重解析

```http
POST /api/admin/log-analysis/reparse
```

请求必须至少指定时间范围、包名、失败状态或旧解析器版本之一；禁止无条件全量同步执行。接口创建受限任务并返回任务 ID，任务状态可查询。单任务范围、并发数和批次大小必须受限。

### 8.7 现有事件接口

`GET /api/admin/events` 保留。包名、设备 ID、日志级别继续完全匹配；`date_from/date_to` 改为北京时间自然日边界；所有时间字段转换为 `+08:00`。

## 9. 前端交互设计

### 9.1 页面结构

日志页提供两个视图：

1. **解析统计**：默认视图；
2. **原始日志**：保留现有日志列表和详情。

解析统计顶部包含：开始日期（北京时间）、结束日期（北京时间）、包名、设备 ID、日志级别、查询、刷新、重置和“配置指标”。页面显示当前生效条件，查询和分页失败保留上一批有效数据。

### 9.2 聚合表

默认列：

1. 日期；
2. 包名；
3. 别名；
4. 网页 URL；
5. 公司；
6. 账户；
7. 用户数；
8. 流程日志数；
9. 计划点击数；
10. 实际点击数；
11. 广告区域点击数；
12. 插屏展示数；
13. 插屏点击数；
14. 平均流程耗时；
15. 成功完成率；
16. 解析失败数。

宽表允许横向滚动，首要识别列可固定。数值列支持服务端排序。比例采用明确颜色但不能只依赖颜色表达状态。

别名、公司、账户单元格支持直接编辑：

- 未配置时显示为空；
- 点击进入编辑；
- 保存期间禁用重复操作；
- 成功后刷新同包名的所有行；
- 失败保留输入并显示错误；
- 空值保存表示清空配置。

### 9.3 指标配置

“配置指标”弹窗展示可见列和隐藏列，支持：

- 从隐藏区添加列；
- 从可见区移除列；
- 调整可见列顺序；
- 恢复系统默认；
- 保存为全局配置。

日期和包名建议作为强制列，不允许同时隐藏，确保表格仍可识别分组。配置保存失败时保持弹窗及用户选择，不覆盖服务端有效配置。

### 9.4 明细与详情

点击聚合行进入明细抽屉或子页面，显示北京时间、包名、设备、URL、关键解析指标、最终原因和解析状态。点击明细打开完整详情，分区展示：

- 关键摘要；
- 点击计划与实际结果；
- 插屏与页面状态；
- 完整解析 JSON；
- 原始 `extra`，支持复制。

解析失败记录仍可进入详情并查看原文和安全错误摘要。

## 10. 数据迁移与回填

迁移分阶段执行：

1. 备份数据库；
2. 新增解析结果表、包名资料表和全局配置表；
3. 部署兼容旧数据的新代码；
4. 用小范围日志验证解析器；
5. 按时间分批回填历史 `event_type=log` 事件；
6. 每批记录扫描数、成功数、unsupported 数、failed 数和最后游标；
7. 验证原始事件总数、分区行数和原始 `extra` 校验摘要不变；
8. 启用解析统计页面；
9. 重建或替换北京时间统计视图并验证日边界。

历史回填必须：

- 支持 dry-run；
- 支持断点续跑；
- 使用稳定游标 `(server_ts, id)`；
- 使用 upsert，重复执行不产生重复结果；
- 不更新 `sdk_events.payload`；
- 不输出完整 `extra`；
- 提供批次大小和范围参数；
- 失败时只回滚当前批次。

## 11. 错误处理与安全

- `extra` 必须仍为字符串；超过在线解析上限时原始事件照常保存，解析标记 failed；
- 解析器不得访问网络、文件系统、子进程或动态执行输入；
- 对嵌套列表和字段数量设置上限，防止恶意输入放大内存；
- 所有 Admin 新接口继续使用 Admin Token；
- 包名资料和列配置更新记录更新时间，服务日志只记录包名和操作结果；
- 重解析任务限制日期跨度、批次大小、并发数和任务频率；
- 原始 `extra` 只在单条详情中返回，不进入聚合接口；
- 解析失败不得阻断 SDK 日志上报，也不得使整个日志批次回滚。

## 12. 测试策略

### 12.1 时间测试

- UTC 时间正确序列化为 `+08:00`；
- 北京时间 00:00 前后映射到正确 UTC 边界；
- 单日、跨日、月底、年底日期筛选；
- 今日/昨日、按日/小时统计使用北京时间；
- 无时区 datetime 被拒绝或按明确的数据库约定处理，不能静默猜测；
- 历史数据无需更新即可得到正确显示。

### 12.2 解析器测试

- 使用提供脚本中的固定样例和已知 `H1` 日志建立测试向量；
- 新模块输出与原脚本关键字段一致；
- 一个 `extra` 含多条日志时顺序稳定；
- unsupported、格式错误、超长输入、极深嵌套和未知字段；
- 中文词库输出使用 UTF-8，不出现乱码；
- 解析相同输入多次结果一致；
- 解析器升级和历史重解析幂等。

### 12.3 API 与聚合测试

- 完全匹配筛选正确；
- 北京日期转换为正确 SQL 参数；
- 聚合口径和有效样本数正确；

### 12.5 生产验收

- 数据库备份可被 `pg_restore --list` 读取；
- 迁移前后 `sdk_events` 总数、分区数和非空 `extra` 数一致；

- 回滚应用版本不需要回写或删除原始事件。

## 13. 发布与回滚

发布顺序：数据库备份 → 新表迁移 → 后端兼容代码 → 前端 → 小范围回填 → 验证 → 分批历史回填 → 北京时间统计视图切换。

应用回滚时：

- 恢复上一版本后端和前端；
- 保留新增解析表和配置表，不影响旧代码；
- 暂停回填/重解析任务；
- 不回滚或重写 `sdk_events`；
- 若北京时间物化视图影响旧版本，按部署备份恢复旧视图定义。

## 14. 验收标准

1. 所有面向业务的日期和时间以 UTC+8 返回与展示；
2. 数据库历史绝对时间不被整体加八小时；
3. 日期筛选及今日、昨日、日/小时统计以北京时间为边界；
4. 包名、设备和级别完全匹配筛选真实生效；
5. 提供的解析脚本样例与在线解析关键字段一致；
6. 原始 `extra` 保留且可追溯，解析失败不影响上报；
7. 历史回填可中断、继续、重复执行且不产生重复结果；
8. 聚合页可下钻至解析明细和原始日志；
9. 别名、公司、账户未配置显示为空，并可直接新增、修改和清空；
10. 指标列可全局添加、移除、排序和恢复默认；
11. 聚合缺失值、样本数、平均值和成功率口径符合本设计；
12. 迁移和回填前后原始事件数量与内容不变；
13. 新增接口受 Admin Token 保护并限制查询/重解析范围；
14. 后端、前端、迁移、解析器和生产冒烟测试全部通过后方可部署。
