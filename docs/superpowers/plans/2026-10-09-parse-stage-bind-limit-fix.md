# 解析阶段批量写入参数超限修复计划

> 面向执行窗口：使用 executing-plans 和 test-driven-development 执行；主窗口负责决策与审查，独立审查窗口负责验收。

**目标：** 修复生产任务 14–17 的 asyncpg 32,767 参数超限，不改变解析口径、查询条件或 SDK 协议。

**架构：** 保持每批读取最多 200 条原始事件及现有并发解码。仅将展开后的 H1、点击暂存记录分为参数安全的小块，所有块、暂存清理、计数及游标推进仍处于同一个批次事务；任一块失败则整批回滚。

**技术栈：** SQLAlchemy、asyncpg、PostgreSQL、pytest。

| 任务 17 下一批 200 事件 | 1535 / 30700 | 3036 / 51612 |
| 任务 14 首批 200 事件 | 1833 / 36660 | 3590 / 61030 |

同生产 asyncpg 0.30.0 只读 SELECT：32767 参数成功，32768 参数抛 InterfaceError。

## 修改文件与边界

- `backend/app/services/log_parse_job_service.py`：暂存 H1 / 点击 INSERT 分段；参数预算保守不超过 30000，且最多 1000 行一段；不修改 publish 的 SQL 或业务字段。
- `backend/app/workers/log_parse_worker.py`：异常分支记录 job_id 与完整异常堆栈，禁止输出请求 payload、token、密钥或 SQL 参数。注意 SQLAlchemy 异常字符串可能携带参数，不可直接无保护 logger.exception 泄漏日志内容；使用安全异常链/去参数日志或局部参数隐藏，并测试脱敏。
- `backend/tests/test_log_parse_job_service_v2.py`：参数限制和事务回归。
- `backend/tests/test_log_parse_worker.py`：异常记录及失败终态回归。
- 新增修复验收、部署记录，不修改数据库结构或前端业务代码。
